### D-01 Android 엔진: Chromium 포크 대신 시스템 WebView (2026-11-03)
- **결정**: Android System WebView(=Chromium)에 앱 코드를 붙인다.
- **이유**: Chromium 포크는 소스 100GB 이상에 빌드가 수 시간 걸리고, 보안 패치도 직접 따라가야 한다. 엔진 레벨의 핵심 효과는 `onWindowVisibilityChanged` 오버라이드와 `setRendererPriorityPolicy`로 대신할 수 있다. 사례 조사에서도 YTPro와 NouTube가 같은 방식을 쓴다.
- **대안**: Brave식 포크, Custom Tabs(JS 주입 불가라 탈락).

### D-02 iOS 엔진: WKWebView (2026-11-03)
- **결정**: WKWebView를 쓴다.
- **이유**: App Store 지침 2.5.6에 따라 WebKit 사용이 필수다. BrowserEngineKit은 EU 한정이고 별도 요건이 많다.

### D-03 Premium 확인을 우회하는 기법은 구현하지 않음 (2026-11-03, 사례 조사 후 재확인)
- **결정**: 다음은 넣지 않는다.
  - User-Agent 위장
  - 스트림 URL 추출
  - **YouTube가 스스로 건 pause를 주기적으로 되돌리는 guard**(NouTube `background-guard.ts`, FixYTBackground)
  - 가짜 키·포인터 입력(keep-alive)
- **이유**: 2026년 1월부터 YouTube는 비 Premium 계정의 백그라운드 재생을 의도적으로 막고 있다(Google 확인). 위 기법들은 그 차단을 정면으로 피해 가는 것이다.
- **하는 것**:
  - Brave 수준의 가시성 위장
  - **엔진(WebKit/Chromium)이** 건 정지만 재개
  - OS 레이어(서비스, 오디오 세션)
  - Premium 계정이 정상적으로 백그라운드 재생하도록 받쳐 주는 것
- **열린 질문**: "계속 시청하시겠습니까?" 대화상자는 Premium 사용자에게도 몇 시간 뒤에 뜬다. 자동 확인 여부는 실기기에서 확인한 뒤 따로 결정한다.

### D-04 스크립트는 앱에 포함하고 document-start에 주입 (2026-11-03)
- **결정**: `bgplay.js`는 앱 번들에 넣고 document-start에 주입한다.
- **이유**: 페이지 스크립트보다 먼저 실행돼야 위장이 확실하다. YTPro는 `onPageFinished`에 jsDelivr `@latest`를 원격으로 받아 실행하는데, 너무 늦고 공급망 위험(SmartTube 사고 참고)과 스토어 정책 문제가 있다.

### D-05 Android에 `navigator.mediaSession` 폴리필 (2026-11-03)
- **결정**: Media Session API가 없을 때만 최소 구현을 정의한다.
- **이유**: Android WebView에는 이 API가 없는 것으로 보인다(YTPro 코드에서 추론). 폴리필을 넣으면 YouTube가 넣어 주는 제목, 아티스트, 아트워크, 다음/이전 핸들러를 그대로 알림에 쓸 수 있다.
- **검증**: API를 지운 Chromium에서 테스트 통과(`bgplay.test.mjs` 12번).

### D-06 보관함 UI·로직은 공용 웹 모듈로 (2026-11-03)
- **결정**: `shared/web/library/`(HTML/CSS/JS)를 두 플랫폼이 투명 WebView 오버레이로 띄운다. 네이티브는 저장, 표시, 재생만 맡는다.
- **이유**:
  1. 두 플랫폼의 UX가 같아지고 코드가 한 벌이다.
  2. 이 개발 환경에는 Android SDK와 Xcode가 없다. 그래서 **Chromium에서 실제로 화면을 조작하며 테스트할 수 있는 유일한 형태**다(UI 테스트 11개, 스크린샷).
  3. 앱 안에 이미 WebView가 있어 추가 런타임 비용이 작다.
- **대가**: 완전한 네이티브 느낌은 덜하다. 오버레이 WebView 하나만큼 메모리를 더 쓴다.
- **대안**: Kotlin/Swift 네이티브 UI 두 벌(검증 불가, 중복). React Native/Flutter 전환(기존 네이티브 재생 코드를 다시 짜야 함).

### D-07 카테고리는 여러 개 소속 가능 + 태그 여러 개 (2026-11-03)
- **결정**: 한 곡이 여러 카테고리(=플레이리스트)에 들어갈 수 있다. "임시함"은 어느 카테고리에도 없는 곡이다.
- **이유**:
  - 사용자 요청이 "플레이리스트 종류 카테고리"이고, 같은 곡을 운동과 드라이브에 동시에 넣는 것이 자연스럽다(YouTube, Spotify 모델).
  - 이 정의라면 "분류 완료" 판정도 명확하다(카테고리 1개 이상).
  - 사례 조사는 MVP에 카테고리 1개를 권했지만, 판정 모호성 문제가 위 정의로 해소된다.
- **대안**: Todoist식 카테고리 1개 + 태그 여러 개.

### D-08 임시함은 저장하지 않고 계산 (2026-11-03)
- **결정**: inbox 목록을 따로 두지 않는다. `items - (모든 카테고리의 곡)`으로 계산한다.
- **이유**: 두 목록을 맞추는 버그(분류했는데 임시함에 남음 등)가 원천적으로 사라진다. 카테고리를 지우면 곡이 자동으로 임시함에 돌아온다.

### D-09 중복 저장은 바꾸지 않고 위치만 알려줌 (2026-11-03)
- **결정**: 이미 있는 곡을 "＋ 임시"로 다시 저장하면 데이터를 바꾸지 않고 "이미 저장됨 · 운동"과 [분류]를 보여준다. 단 비어 있던 메타데이터는 채운다.
- **이유**: 실수로 두 번 눌러도 안전하다. 분류된 곡이 임시함으로 되돌아가지 않는다.
- **다음 단계 후보**: 저장 횟수(`saveCount`)를 관심도 신호로 쓰기(CASE_STUDIES §4.3-C).

### D-10 재생 큐는 네이티브가 진행 (2026-11-03)
- **결정**: 보관함은 큐(곡 URL 목록과 시작 위치)를 네이티브에 넘긴다. 네이티브가 `ended`를 보고 다음 페이지를 연다. 사용자가 다른 영상으로 가면 큐가 끝난다.
- **이유**: 보관함 오버레이 WebView는 백그라운드에서 멈출 수 있다(특히 iOS). 재생 중인 WebView의 상태는 네이티브가 이미 받고 있다.
- **위험**: iOS 백그라운드에서 새 페이지 재생 시작이 막힐 수 있다. 끝나기 직전 미리 넘기기(FixYTBackground pre-advance)를 검토한다.

### D-11 브리지 보안: 출처 검증으로 (2026-11-03)
- **결정**:
  - 재생 WebView: Android는 `addWebMessageListener`의 origin 규칙(`*.youtube.com`), iOS는 `frameInfo`(메인 프레임 + YouTube 호스트)로 검증한다.
  - 보관함 WebView: Android는 `appassets.androidplatform.net` origin만, iOS는 `file:` 출처만 받는다. 다른 페이지로는 이동이 막혀 있다.
- **참고**: NouTube는 브리지 토큰을 쓴다. 재생 WebView의 메시지는 재생 상태(표시용)뿐이라 위조돼도 영향이 작아 토큰은 보류했다.

### D-12 스토어 심사 회피 기법을 쓰지 않고, 출시는 이중 트랙으로 (2026-11-03)
- **결정**:
  - 심사 중 기능 숨김, 출시 후 원격 플래그나 원격 스크립트로 기능 켜기, 정체를 숨기는 이름·설명, Enterprise 인증서 배포, 다른 계정으로 재출시를 하지 않는다.
  - 스토어에는 백그라운드 위장 코드가 **바이너리에 없는** `store` 빌드(보관함 우선, 재생은 공식 앱으로 위임)를 내고, 풀 기능은 스토어 밖(사이드로드, TestFlight 내부)으로 쓴다.
- **이유**:
  - Apple 2.5.19·2.3.1 위반은 앱 하나가 아니라 **개발자 계정 해지**로 이어진다.
  - YouTube 신고로 인한 사후 삭제 사례(ProTube, Musi, Kiwi)가 있다.
  - 이번에 만든 핵심 기능(빠른 저장 → 분류)은 재생을 공식 앱에 맡겨도 그대로 쓸모가 있다.
- **근거와 상세**: [STORE_RELEASE.md](STORE_RELEASE.md)
- **상태**: 결정만 함. 구현은 HANDOFF T-20~T-25

### D-13 앱 이름을 Youplay로 변경, 내부 식별자는 보류 (2026-11-04)
- **결정**: 사용자 요청으로 화면에 보이는 앱 이름을 **Youplay**로 바꾼다. 대상은 Android `app_name`, iOS `CFBundleDisplayName`, 상단 바 라벨, 잠금화면 기본 제목, 보관함 페이지 제목, 문서.
  - 내부 식별자는 그대로 둔다: `io.github.bgplay`(applicationId/번들 ID/패키지), `bgplay.js`, `BgPlayNative`/`__bgplay`/`BgLibNative`, Xcode 타깃·폴더 `BgPlay`, `bgplay://`, 로그 태그.
- **이유**:
  - 스토어에 한 번 올린 앱 ID는 바꿀 수 없으므로, 이름 검토(아래)가 끝난 뒤 한 번에 정하는 것이 낫다.
  - 지금 일괄로 바꾸면 빌드로 확인할 수 없는 환경에서 Android·iOS·공용 코드를 동시에 건드리게 된다(T-26으로 분리).
- **이름 관련 확인 필요(스토어 출시 전)**:
  1. "You" + "play" 조합과 빨간 재생 아이콘이 YouTube와 혼동된다는 지적을 받을 수 있다(STORE_RELEASE A4/G3, Apple 5.2.1, Play 사칭 정책).
  2. 같은 이름의 앱이 이미 있을 수 있다. 사례 조사 중 "YouPlay"라는 네이티브 오디오 추출 앱이 검색됨(CASE_STUDIES §2.2 기타).
  3. 상표 검색(KIPRIS, USPTO, EUIPO)과 App Store/Play 이름 검색을 한다. 스토어용 빌드는 다른 이름을 쓸 수도 있다(STORE_RELEASE §5 "store" 빌드 이름).
- **상태**: 표시 이름 변경 완료. ID 확정은 HANDOFF T-26
